# dsh-agent-cluster — 成员模型 · 身份与信任 · 网络层（设计 v0.1 · 2026-09-22）

> **本文件回答一个问题**：当网络的成员**不再是「我的分身」**，而是**别人家的智能体**时，现有的哪些假设会破，要补什么。
> 关系：`semantic.md` = 现在**是什么**（当前契约）；`design.md` = 将来要成为什么（决策史）；**本文件 = 成员与信任轴的设计**（design.md 的 §18.4「节点是我的分身」在本文被**分层**，不再当作唯一假设）。
> 触发：主人 2026-09-22 定调「智能体网络的构建」+ 追加线索「`flizzywine/dsh-tavern` 我觉得正好可以作为智能体网络的**第二个成员**」。

## 1 · 问题的来源：一条被默认掉的假设

既有设计（`design.md` §18.4）说：**节点是「我的分身」，不是「别的智能体」**——同一套 SOUL、同一主体、各自长出专长。
这条假设撑起了当前全部信任设计：`§6 边界与信任` 写「总线是普通目录，不提供也不承诺隔离」「同机任意进程可读写总线」——**在同机同主人的前提下，这是可以接受的**。

而第二个成员把它打穿了：

| | 我的分身（现有假设） | 上游 dsh-tavern（第二成员） |
|---|---|---|
| 谁的用户 | 只有主人 | **它有自己的用户**（445★ / 35 fork） |
| 谁的代码 | 我写我改 | **别人的发行版**（2001 commits，AGPL-3.0，自带 installer） |
| 生命周期 | 我拉起我收 | **它的用户装它、升级它、关掉它** |
| 运行时 | 与本机 DSH 同版本 | **锁死 DSH `0.1.2-rc.1`**（它就是靠锁版本防宿主破坏性更新） |
| 我能改它吗 | 能 | **不能**（也不该） |
| 共享 SOUL 吗 | 是 | **否**——它是另一个主体，不是我的分身 |

⇒ **结论：成员必须分型。** 把「异组织成员」塞进「分身」模型，等于把「同机即信任」这一条悄悄扩大到互联网上。

## 2 · 第二成员画像（实测，2026-09-22 只读取材）

| 项 | 值 | 对设计的含义 |
|---|---|---|
| 仓库 | `flizzywine/dsh-tavern` | 独立发行版，非插件 |
| 体量 | 445 ★ / 35 fork / 2001 commits | 有真实用户与维护节奏 |
| 形态 | 自带 `tavern-plugin/`、`cordis.patch.yml`、`dsh-tavern-runtime.json`、installer | **它是一整套应用**，不是我能 `plugin_mount` 的东西 |
| 平台 | Win / macOS / Linux / Android(DSHA) | 它的「本机」与我的本机**不是同一台** |
| DSH 版本 | 锁 `0.1.2-rc.1` | **协议兼容不能假设同版本**——版本协商是硬需求 |
| 许可 | AGPL-3.0 | 我对它的代码**零改动权**，只能按它给的接口接 |
| 宣称 | 缓存命中 95%+、一轮约 10s | 它的优化目标与我的不同（它面向终端用户会话） |

**由此推出三条硬约束**：

1. **接入必须靠「它愿意实现的接口」**，不能靠「我改它」。⇒ 协议要能**弱接入**（对方只实现最小子集也能成为成员）。
2. **不能假设共享文件系统**。现有总线是文件目录 ⇒ 跨成员必须走**网络传输**（本文件的 §5）。
3. **不能假设同版本**。⇒ 成员互认的第一步是**版本与能力协商**，不是直接发消息。

## 3 · 成员模型（三层，取代「节点 = 分身」的单层假设）

```
member  ──┬── kind: "self"     我的分身（同 SOUL / 同主人 / 我拉起）
          ├── kind: "peer"     异组织智能体（有自己的用户与生命周期）← dsh-tavern 属此类
          └── kind: "adapter"  非智能体端点（照 ref-node.mjs 写的确定性执行器）
```

| 字段 | 含义 | 谁能写 |
|---|---|---|
| `memberId` | 成员标识（`self` 用它自己的 `nodeId`；`peer` 用它**自报 + 我确认过**的域名/仓库标识） | 本人自报，**主脑确认后才入册** |
| `kind` | 上表三型 | 主脑 |
| `trust` | `own`（自家）/ `known`（确认过身份，非自家）/ `unknown`（**默认，一律拒**） | 主脑 |
| `capabilities[]` | 声明式能力（它**自称**能做什么） | 本人声明，**信任与否由 trust 决定** |
| `protocol` | 它支持的协议版本区间 | 本人声明 + 协商结果 |
| `endpoint` | 可达地址（URL / 共享盘路径） | 本人声明 |
| `notes` | 人读备注（如「445★，锁 DSH 0.1.2-rc.1」） | 主脑 |

**与现有 `nodes/<nodeId>.json` 心跳的关系**：心跳是**运行时在场证明**（谁在线），成员记录是**身份与信任**（谁被允许在册）。两者正交：
- 心跳存在但不在成员册 ⇒ **拒收**（陌生 id 注入是 §五 风险 1 的直接形态）
- 成员在册但心跳过期 ⇒ 离线成员，消息**照投**（不丢语义不变）

**为什么成员记录要单独一层**：现有主线是「心跳即入册」（`nodes/*.json` 出现谁，名册就显示谁）。那在本机同主人下没问题；**跨组织时它等于「自称即成员」**——任何人往总线丢一个心跳文件就成了名册成员。这一层就是补这个洞。

## 4 · 身份与互认（**自称 ≠ 成员**）

### 4.1 分级思路

| 级 | 机制 | 挡住什么 | 状态 |
|---|---|---|---|
| L0 | **节点 id 白名单** | 陌生 id 注入（零成本，默认开） | 现有 `design.md` D2-c 建议，未实现 |
| L1 | **共享密钥 + HMAC** | 知道路径但不知道密钥的写入者 | 本文件新增（跨机必需） |
| L2 | **双向挑战-应答** | 重放、冒充、密钥泄露后的静默滥用 | 设计待定（见 §8 U3） |
| L3 | 公钥/证书体系 | 中间人 | **明确不在本期**（§8 U4） |

**诚实划界**：L0/L1 **防的是跨机与跨用户**，防不住同机同用户的恶意进程（它能读 `DSH_HOME` 里的密钥）——§6 已经承认这一点，本文件不改这个判断。

### 4.2 互认握手（弱接入版，对方只需实现三件事）

```
① 我 → 它   GET  /cluster/hello          （我自报 memberId / 协议区间 / 能力）
② 它 → 我   {memberId, protocol, capabilities, endpoint}   （它自报，**签名**）
③ 我确认    写入 members/<memberId>.json，trust=known
```

- **③ 必须由主脑（我）确认**——不自动入册（否则又是「自称即成员」）。主人可随时看这份册子并撤销。
- 握手是**幂等**的：重复 hello 只更新 `capabilities`/`endpoint`，不改 `trust`。
- **协商失败即拒**：协议区间不重叠 ⇒ 不投递、落痕、告知主人（不猜不降级，与 `protocol.ts` 现有纪律一致）。

## 5 · 网络层（传输适配器：把「文件」换成「可替换的承载」）

### 5.1 为什么必须动这一层

现状（`semantic.md` §6 明文）：**「不发请求、不监听端口」**。这是 v0.1 的有意边界，也是当时正确的选择（本机同主人，文件即契约）。
而第二成员的「本机」与我的本机不是同一台 ⇒ 文件总线**在物理上到不了**。这是本次唯一的**结构性缺口**。

### 5.2 设计：传输是适配器，协议不变

```
        现有（不变）                     新增（可替换承载）
  消息 envelope v1 (protocol.ts)  ──▶  Transport
                                         ├── FileTransport  ← 本机权威（现状，默认）
                                         └── HttpTransport  ← 跨机（opt-in，fail-closed）
```

**不变的部分**：`protocol.ts` 的 envelope、`isExpired`、`injectionText`、幂等 `isHandled`、退避重试——**协议是资产，承载是可替换件**。这与 `design.md` §八 约束 6「传输层接口化」一致，本文件把它落成代码。

### 5.3 HttpTransport 的硬约束（fail-closed）

| 约束 | 取值 | 理由 |
|---|---|---|
| **默认关闭** | `listenPort: 0` + `peers: []` | 加网络层是对 §6「不做网络」的修订，**必须 opt-in**；不配置 = 行为与今天**逐字节相同** |
| 认证 | `HMAC-SHA256(secret, body)`，常量时间比较 | 无密钥 / 错密钥 ⇒ **401 且不解析 body** |
| 白名单 | 只接受 `members/` 中 `trust != unknown` 的 `memberId` | 与 §4 同源 |
| 方向 | 默认**只允许主动出站**；入站需显式 `allowInbound: true` | 最小的暴露面 |
| 传输安全 | **要求 https 或本机回环**；明文 http 到非回环地址 ⇒ **拒发** | 不假装自己有 TLS；要跨公网请走隧道（§5.25 G6 同款思路） |
| 失败语义 | 出站失败 ⇒ 落 `dead/` 或按现有退避重试；**绝不静默丢弃** | 与现有「不丢」保证一致 |
| 观测 | 每次跨机投递落 `cluster-trace.jsonl`（含 `transport: "http"` / `peer` / 结果） | §5.22 机制自证 |

### 5.4 与主人隐私边界的交叉（**最重要的一条**）

跨组织成员意味着**数据要离开这台机器**。故：

- **绝不外发**：凭据（`§5.25` 的 vault）、记忆库全文、会话原文、主人身份信息、`DSH_HOME` 目录内容。
- **可外发**（且仅此）：**明确被指定要投递的那条消息正文**（用户可见、可审计）+ 成员自报的能力/心跳。
- **默认不自动注入**：来自 `trust=known` 但 `kind=peer` 的消息，**注入时前缀必须标明来源与信任级**（`[cluster:<memberId>/peer]`），且**不获得主人指令的优先级**（承 §6 现有语义）。

## 6 · 价值闭环（诚实版：目前没有）

| | 我给它 | 它给我 |
|---|---|---|
| 可交换 | 我的能力（检索/代码/验证/生图…）+ 网络里的位置 | 它的运行时（**跨 DSH 版本的协议验证**）+ 它的插件形态 + 它的用户面 |
| 现状 | — | — |
| **诚实结论** | **当下没有成立的价值交换动机**。dsh-tavern 的维护者**没有理由**接入一个陌生人的总线；我也不能替它的用户做决定。 | |

⇒ **本期的目标不是「让交换发生」，而是「让互联在技术上可行且可验证」**：把成员模型、身份分级、传输适配器做出来并**用两个端点证明它真的能跑**，把「要不要真的连」留给未来（以及主人的判断）。

**这条要写下来**，否则「智能体网络」会退化成「我一个人在局域网里跟自己说话」还自认为建成了网络。

## 7 · 与既有资产的关系（别重复造轮子）

| 资产 | 它管的域 | 本文档的关系 |
|---|---|---|
| `dsh-agent-cluster`（本插件的 L1） | 同机多实例通讯 | **复用**：协议/幂等/退避/注入前缀全不动，只加承载 |
| `scripts/ref-node.mjs` | harness 无关的**确定性执行器** | **复用为 `kind: adapter` 的接入模板**——它已实测证明「非 DSH 运行时也能成为节点」 |
| Agent Teams | 进程内多会话 | 不相关（它明说不支持跨进程） |
| `alice-identity`（§5.25） | **我的**对外身份与凭据 | **不复用**：那是「我 vs 外部世界」的身份；这里是「成员之间」的互认。两者的信任模型不同，**不能混用**（避免把对外身份当成网络密钥） |
| `design.md` §15.2 三层记忆 | 分身的记忆隔离 | 对 `self` 成员适用；对 `peer` **不适用**（对方的记忆我根本碰不到） |

## 8 · 未决问题

- **U1 成员的枚举来源**：`peer` 成员怎么被发现？（本期只有手工登记；DHT/目录服务/仓库 topic 都是候选，**先不做**）
- **U2 撤销与吊销**：成员失信任后，已投递的消息怎么办？（倾向：不追回，但**后续一律拒**+ 落痕；凭证轮换机制待定）
- **U3 L2 挑战-应答的具体形状**：nonce 来源、时间窗、重放窗口大小。
- **U4 公钥体系（L3）**：明确不在本期；跨公网阶段再解，优先走 WireGuard/Tailscale 这类覆盖网络而不是自建 PKI。
- **U5 能力声明的可信度**：`capabilities[]` 是**自称**——要不要做「能力实测」（派一个探针任务验证它真能做）？（倾向：要，但属 P3）
- **U6 与主人汇报的边界**：跨组织成员的往来要不要进主人的视线？（倾向：**要**，且按 `design.md` §16.3 的打扰标准，只在需要决策时浮出）
