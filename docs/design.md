## 一 · 能力边界（先划清楚，再谈设计）

### 1.1 能做（v0.1 已实测）

| 能力 | 判据 |
|---|---|
| 本机任意数量 DSH 实例互通（跨 profile / 跨 DSH_HOME / 跨端口） | A1 名册实测：两个节点互见、带角色与心跳年龄 |
| 点对点消息 → 注入对方会话 | A2 实测：会话真实收到 `[cluster:<from>] …` |
| 广播（离线节点也投，上线即收） | A3 实测：消息落到目标收件箱 |
| 不丢（原子发布 + 归档 + 退避重试 + 死信） | A5 实测：搁浅消息被接管后仍 `delivered` |
| 在线名册与判活（心跳 + TTL，判据单源） | A6 单测 + 实测 |
| 坏数据不崩、观测不反噬（轨迹吞错） | A7/A10 尸体测试 |

### 1.2 不能做 / 不该指望（诚实清单）

1. **不是强一致**：文件系统语义，无事务、无跨节点原子操作；名册是**最终一致**视图，没有全局一致时刻。
2. **不是安全边界**：同机任意进程都能读写总线；v0.1 无签名/无加密——**能写总线的人就能往 agent 上下文里塞文本**（见 §五 风险 1）。
3. **不是沙箱**：插件与宿主同进程、全权限（DSH 现状，能力 ≠ 隔离）。**插件 bug 会杀死宿主**——今天刚用一次真实崩溃换来这条纪律。
4. **无中心调度**：没有 leader、没有仲裁、没有全局队列。
5. **无实时保证**：v0.1 是轮询模型，延迟 = 周期（默认 2s）+ 处理时间；**没有 push 通道**。
6. **不替 agent 决策**：只投递，不自动应答、不解析指令、不授予特权。
7. **跨机受限**：DSH web 只监听 loopback（官方明确拒绝 `0.0.0.0`）；跨机只能靠共享盘（文件总线可）或自建认证的 HTTP（需自己做密钥/TLS）。
8. **有规模上限**：名册 200 节点、已处理集滚动 500、正文 8000 字符——几百节点的场景需要换设计（不是本方案的目标）。

## 二 · 工作台的三层能力

```
L3 工作台   面板 · 观察者 · 跨实例任务池 · 人工介入点
             ▲
L2 协作语义 task/result 状态机 · 回执 ack · 按角色寻址 · 结果汇总
             ▲
L1 通讯底座 身份 · 名册 · 点对点/广播 · 收件箱 · 不丢 · 会话注入   ← v0.1 已完成
```

- **L1（已完成）**：把「消息送到」做对——这是地基，也是唯一必须绝对可靠的一层。
- **L2（建议下一版）**：把「协作说得清」做对——状态机、回执、寻址、汇总。**不需要新传输**，全部可以用 L1 的消息表达。
- **L3（按需）**：把「人和全局看得见」做对——面板、观察、人工介入。

**分层的意义**：每层只依赖下一层的**消息语义**，不依赖具体传输。将来加 push 通道或换存储，L2/L3 不动。

## 三 · 关键决策点（需主人拍板）

### D1 延迟 vs 简单：要不要 HTTP 推送？

- 现状：纯文件轮询，2s（可配 500ms）。
- 若做 push：**不能**白拿宿主的 browser-auth（cookie 按 authority 绑定、跨端口不复用）；须自建密钥认证。
- **我的建议：先不做。** 2s 对本机协作足够；push 的复杂度（认证/密钥/端口发现/失败回退）远高于收益。真需要时只作为**加速通道**，文件总线仍是权威（"不丢"的保证不变）。

### D2 信任模型：同机即信任，还是签名？

- 风险现实：一条伪造的 `[cluster:…]` 消息会直接进 agent 上下文。
- 选项：a) 同机信任（现状）；b) 每条消息 HMAC 签名（总线密钥）；c) 发送方白名单（只接受已注册节点 id）。
- **我的建议：c 默认开（零成本）+ b 可配置（跨机共享盘时开）**。白名单挡住"陌生 id 注入"；签名挡住"知道目录但不知道密钥"。注意：同用户进程仍可读 DSH_HOME 的密钥——**它防的是跨用户/跨机，不是同用户恶意进程**。

### D3 要不要中心协调者？

- 选项：a) 全平权（现状）；b) 一个"主脑"节点承担调度；c) 常驻 broker 进程。
- **我的建议：a（保持无中心）**，但允许"主脑"作为**角色约定**而非代码特权——想当主脑就是配置 `role: 主脑` + 自己发任务消息。理由：中心 = 单点，挂了全瘫；调度需求用 L2 的消息语义就能表达。

### D4 面板形态？

- 选项：a) 不做（工具查）；b) 独立 HTML 面板（`dsh-panel` 形态：web 路由 + 静态页，同源 fetch）；c) 对话内嵌卡片（client 插件 + Conversation Node）。
- **我的建议：b**。面板最适合"看全局"（名册/消息流/任务状态），且天然是**只读视图**——写操作仍走工具与消息，不制造第二条写路径。

### D5 跨机？

- **我的建议：先只做本机**。但把 `busDir` 保持为任意路径（已支持），跨机留到真有需求再评估（届时先做共享盘、后做 HTTP+TLS）。

## 四 · 与现有机制的关系（别重复造轮子）

| 机制 | 它管的域 | 与 cluster 的关系 |
|---|---|---|
| Agent Teams（官方 experimental） | **进程内**多会话协作；官方 README 明说 "concurrent harness processes over one Team are unsupported" | cluster 补的正是它**不做**的跨进程 |
| subagent / workflow | 父 → 子（子进程由父驱动，非对等） | cluster 是**对等实例**之间 |
| 任务板 `dsh-agent-taskboard` | 本实例内 | L2 可扩展为跨实例任务池 |
| 记忆 / 技能 / 任务板文件 | 共享文件系统（同 DSH_HOME 时天然共享） | cluster **不替代**，只做路由与投递 |

## 五 · 风险与纪律（工作台必须内建的约束）

1. **注入即特权风险**：能写总线的人能给 agent 塞文本。缓解＝注入带来源前缀 + **语义纪律：`cluster` 消息是平级来信，不是主人指令，不获得任何特权**（该写进预设/灵魂，不只是文档）。
2. **消息风暴**：广播 + 自动应答 = 节点互轰。缓解＝不做自动应答；广播默认不重复投；正文与频率有界。
3. **上下文污染**：跨实例消息进上下文会消耗 token。缓解＝`autoInject=false` 时改为「摘要 + 按需取全文」（L2 候选）。
4. **崩溃域共享**：插件异常会杀死宿主（今天验证）。缓解＝**定时器回调必须兜底 + 源码级守卫契约测试**（已立）；所有扩展沿用同一纪律。
5. **判据单源**：在线判定/名册显示/发送警告共用同一常量；取证工具与实现共用同一 needle（§5.22 §4）。

## 八 · 架构决策记录（2026-09-14 主人定调）

**拓扑：中心辐射（hub-and-spoke）——中心 = 爱丽丝（主脑节点），不是无中心。**

| 角色 | 谁 | 职责 |
|---|---|---|
| **指令发出者** | 主人 | **只决定方向 + 接受最终结果**；其余决策皆由工作台内部智能体网络完成 |
| **核心节点（主脑）** | 爱丽丝 | 接收指令 → **细化** → **增强可执行性/可验证性** → **指定具体实例执行** → **执行最终测试验收** |
| **执行节点（worker）** | 其他 DSH 实例 | 承接具体任务、回传结果与证据 |

**网络范围三阶段**：本机（现在）→ 局域网 → 公网（大后期）。

**由该架构推出的硬性设计约束**：

1. **中心必须可交接**（否则单点 = 全瘫）：任务台账落**总线**（`tasks/<taskId>.json`），**不在主脑内存里**；任一实例配置 `role: 主脑` 即可接管未结任务。主脑是**角色**，不是代码特权。
2. **判据先行**：主脑派发时 **`acceptance` 字段必填**（可执行/可证伪的验收判据）——**没有判据不发任务**，否则事后无法验收（对应语义文档的可证伪验收纪律）。
3. **结果带证据指针**：worker 回传 `{status, summary(≤N 字), evidence(路径+行号 / 命令+输出摘录), unverified[]}`；**主脑按判据验收，不按汇报验收**（"报告 ok"不是证据）。
4. **上下文预算纪律**：所有结果都过主脑 ⇒ **主脑上下文是瓶颈** → 强制「摘要 + 证据指针」，全文留在总线/文件按需取证。
5. **混合拓扑**：worker 之间可**点对点直接协作**（不必事事过主脑）；但**涉及主人方向的变更必须经过主脑**。
6. **传输层接口化**（为后两阶段铺路）：L2/L3 只依赖 `send/broadcast/inbox` 的**语义**，不依赖"它是文件"——
   - 本机 = 文件总线（现状）；
   - 局域网 = 插件**自开 HTTP 端口**（不碰 DSH 的 web 端口，绕开官方对 `0.0.0.0` 的拒绝）+ 共享密钥；
   - 公网 = TLS + 节点身份（优先覆盖网络 WireGuard/Tailscale，而非自建）。

## 九 · Worker 专一化设计（2026-09-14 主人定调：专一 + 保留基础能力）

**核心澄清：专一不是"能力弱"，而是"工具面窄"。**

- 依据（实测）：上下文里 **72% 是工具 schema**（且压缩回收不掉）——**每减一个工具 = 每一轮请求都省一份固定成本**；而"会不会自己拆任务"是模型能力，不靠工具面堆出来。
- 所以专一化 = 在**全功能基座**上做减法，而不是从零捏一个弱预设。

**基础能力标准 = DSH 自带 `standard`（标准模式）预设**（已取证：`packages/preset/agent-presets/presets/standard/`，含文件编辑/Shell/文件与网页检索/Skills/计划/目标/子代理/工作流）。

**worker 预设 = `standard` 的副本 −（无关工具）+（专用能力）**。

### 9.1 必须保留（worker 干活的最小集）

文件读写编辑 · shell · 检索 · **计划 / todo（子目标形式的硬需求：worker 要自己拆）** · **cluster 通讯工具（收任务、回结果）**。

### 9.2 建议减掉

| 减掉 | 理由 |
|---|---|
| 子代理 / 工作流 | 防 worker 再开分身 → 层级爆炸、成本失控 |
| 预设创作 / 自指工具 | 非主脑不需要（能改运行时的角色只能有一个） |
| 管理类（插件管理 / 守护协议 / 预检） | 主脑专属 |
| **直达主人的通道（telegram 等）** | **架构纪律**：worker 只能与主脑/同伴通讯——否则绕过主脑，"主人只收最终结果"的拓扑就被打穿了 |

### 9.3 预设矩阵（提名，待主人调整）

| 预设 id | 基座 | 加什么 |
|---|---|---|
| `worker-base` | standard −（9.2 四项） | cluster 通讯 + 汇报契约 |
| `worker-code` | worker-base | 代码检索 / 补丁类插件 |
| `worker-research` | worker-base | 联网检索 / 抓取类插件 |
| `worker-media` | worker-base | 生图 / 视频类插件 |
| `worker-op` | worker-base | 攻防靶场类插件 |

**主脑（爱丽丝）= 全量预设 + cluster**：保留全部能力与直达主人的通道——主脑是**唯一对主人负责的节点**。

### 9.4 落地职责（主人拍板）

- **拍板 D2 白名单**：worker 只接受已注册节点（主脑 + 同伴）的消息；未注册 id 一律 dead/ 并落痕。
- **拍板 e（子目标验收）**：worker 回 `{status, summary, evidence, unverified[]}`；主脑**跑判据**验收，不读汇报。

## 十 · MVP 产品设计

### 10.1 MVP 要证明的唯一闭环

```
主人说方向 → 主脑细化（写成带判据的任务） → 派给 1 个 worker
        → worker 自己拆解执行 → 回结果（带证据） → 主脑跑判据验收 → 主人看结论
```

**MVP 验收判据（全部可证伪）**：

| # | 判据 |
|---|---|
| M1 | 主脑能把一条自然语言方向变成 `task` 消息，**含 `acceptance` 判据**，并有台账文件 |
| M2 | worker 收到任务后**自己拆成步骤**（能看出 plan/todo 产物），不是等喂下一步 |
| M3 | worker 回 `result`，含 `status/summary/evidence/unverified` 四字段 |
| M4 | 主脑**跑判据**（复现 evidence）而不是读 summary，并给出通过/不通过结论 |
| M5 | 主人能在面板上看到：名册、任务状态、最终结论三段信息 |
| M6 | 全程 worker **不直接联系主人**（无 telegram 类通道） |

### 10.2 MVP 范围

**做**：L1（已完成）+ L2 最小集（`task`/`result` 两种消息 + 任务台账 + 判据字段）+ `worker-base` 预设 + 1 个真实 worker 实例 + 只读面板。

**不做**（明确排除，防止 MVP 膨胀）：
- 不做多 worker 调度与能力路由（先打通 1 条闭环，再加第二条）
- 不做 push / 局域网 / 公网
- 不做角色体系
- **不做面板上的任何写操作**（只读 ⇒ 零权限模型 ⇒ 零审批面）
- 不做自动重派/超时自动重试（先看清真实需求，再自动化）

### 10.3 前端交互技术选型

**选型：独立 HTML 面板（`dsh-panel` 模式），不做 client 插件。**

| 维度 | 独立面板（选中） | client 插件（不选） |
|---|---|---|
| 构建 | `tsc` + `copy-assets`（简单） | 双 tsc program + tsdown + 模块表纯度门 + HMR |
| 风险 | 低（规范已固化，有先例） | 高（纯度门 / require 失败是常见坑） |
| 场景匹配 | **全局俯瞰**（名册 / 任务队列 / 消息流） | 对话内嵌、上下文相关卡片 |
| 迭代 | 刷新即见 | 需 watcher + 刷新 |

**为什么只读就够**：主人的操作（出方向）本来就在对话里对主脑讲；面板的职责是"看见全局"。
**只读 ⇒ 零写路径 ⇒ 零权限模型 ⇒ 零审批面**——这是 MVP 能做小的关键。

**技术形态**（沿用技能规范）：
- 宿主托管：`ctx.webServer.register({ kind:'exact', path:'/panel/cluster' })` 页面 + `{ kind:'exact', path:'/api/cluster/state' }` 数据
- **exact 路由优先于宿主的 `/api` prefix**（webserver 匹配顺序 exact → longest prefix）⇒ 走同源信任模型，不经 connection 的 cookie 认证；**仅因 DSH web 绑 127.0.0.1 才安全**
- 页面：**独立资源文件** `src/assets/panel.html`（绝不嵌 TS 模板字符串——转义层会放大正则/反斜杠），build 时拷到 `lib/assets`，运行时 `readFileSync`
- 前端栈：**原生 HTML/CSS/JS，零依赖零构建**；数据 `GET /api/cluster/state` 每 2s 轮询（与总线节奏一致）
- 验证：`webops_open` + `webops_eval` 做真实浏览器 DOM 断言（不交还用户）

### 10.4 面板信息架构（三类视图）

| 视图 | 回答的问题 | 字段 |
|---|---|---|
| **名册** | 谁在？能干什么？忙不忙？ | nodeId / role / tags / online / 心跳年龄 / 待办数 |
| **任务** | 在干什么？到哪一步？ | taskId / 判据 / 承接节点 / 状态 / 耗时 / 结果摘要 / 证据链接 |
| **消息流** | 刚刚发生了什么？ | 时间线（发送/投递/开始/完成），可按节点过滤 |

### 10.5 信息反馈契约（三层）

**L-a worker → 主脑（任务结果，必填）**
```jsonc
{ "kind": "result", "meta": {
  "taskId": "t-…",
  "status": "done | partial | failed",
  "summary": "≤300 字结论",
  "evidence": [ { "kind":"file", "path":"…", "lines":"12-40" },
                { "kind":"command", "cmd":"…", "expect":"…" } ],
  "unverified": ["未验证项 + 为什么验不了"],
  "blockedBy": "被阻塞时：缺什么" } }
```

**L-b worker → 主脑（过程信号，最小集）**
- 只要三态：**开始 / 结束 / 阻塞**（**不要进度百分比**——它会诱导虚报）
- 关键中间产物的落盘路径（便于主脑中途取证）

**L-c 主脑 → 主人（阶段播报 + 最终结果）**
- **阶段播报**：细化完成 → 已派发（谁承接、判据是什么）→ 回收 → 验收结论
- **最终结果格式**：结论 + **判据对照表**（判据 → 实测证据 → 通过与否）+ 未验证项 + 遗留风险
- 纪律：**主人的信息只从主脑来**（worker 不直达，见 §9.2）

### 10.6 MVP 还需要主人提供的信息

1. **worker 实例形态**：本机第二个 DSH 用 `headless` profile（一次性任务）还是 `web`（常驻）？
2. **模型路由**：worker 用哪个模型（成本 vs 能力）？
3. **任务预算上限**：单任务允许的工具调用数 / 时长上限（防失控）？
4. **面板入口偏好**：新标签页 `http://127.0.0.1:3080/panel/cluster`，还是嵌在 DSH GUI 里的 iframe？
5. **是否需要中止能力**：MVP 建议不做（只读），主人若要"喊停"则加一个受控写操作。

## 十一 · 前端设计修正（2026-09-14 主人追加两次修正）

> 本节**取代 §10.2「不做任何写操作」、§10.3「托管面板」、§10.4 三视图**。
> （诚实记录：主人提出后当轮我口头声称"已追加进设计"，实际并未落盘——补写于同日晚。教训：**落盘判定看文件，不看话**。）

### 11.1 交付形态：独立桌面应用（Tauri），不是托管面板

- 主人要的是**独立的应用程序**：独立进程 + 独立窗口 + 系统托盘，不寄生在 DSH web 里。
- 工具链已取证具备：Rust 1.93 / Node 24 / WebView2 149。
- **总线目录 = 唯一契约**：应用只读写文件，不需要 DSH 的端口/认证/生命周期；DSH 没起也不报错（显示"无在线节点"）。
- 选型对比：Tauri（~5–10MB、系统 WebView2、托盘通知）> Electron（~150MB）> node web app（无窗口）。

### 11.2 信息设计：驾驶舱，不是监控台

主人原话：「**我可以看到整个的工作过程，但是我不用看工作细节**」。

1. **状态变化 > 动作明细**：只显示阶段推进，不显示调了什么工具 / 读了什么文件。
2. **异常优先，正常安静**：顺利时界面几乎静止；卡住 / 失败 / 需决策才浮出（顶部卡片 + 托盘通知）。
3. **细节按需**：证据（路径 / 命令 / 行号）**不进主人视野**——它属于主脑与 worker 之间的验收流程。

| 区域 | 显示 | 刻意不显示 |
|---|---|---|
| **任务流**（主） | 方向（一句话）→ 阶段条（细化/派发/执行/回收/验收/完成）→ 承接节点名 → 耗时 → 状态色 → 完成后一行结论 | 任务 id、节点 id、路径、命令、消息原文 |
| **节点**（副·轻量） | 显示名 + 负载 + 状态灯 | 心跳、pid、端口 |
| **异常**（顶部） | 需主人决策的事 | — |
| ~~消息流~~ | **删除**（审计范畴，不属于驾驶舱） | — |

### 11.3 受众分层 = 信息分层

- worker → 主脑：全量（`status/summary/evidence/unverified`）——证据供主脑复现验收；
- 主脑 → 主人：只留「**状态 + 一行结论 + 是否需决策**」；
- ⇒ `evidence` 永不进主人视野；这也解释了为何 worker 不需要直达主人的通道。

### 11.4 主人可在工作台内直接与任意节点交互

**修正 §10.2：「只读」→「读 + 有限写」。**

**写的本质 = 往目标节点收件箱写一条合法消息文件**（`mailbox/<nodeId>/<id>.json`，protocol v1）：
**插件零改动**（接收方按普通消息注入会话）；离线节点也能投（不丢，上线即处理）；**无需 HTTP、无需认证**——契约是文件格式，不是 API。

| 设计点 | 取值 | 理由 |
|---|---|---|
| `from` | `owner`（特殊身份常量） | 节点据此区分「主人直连」与「同伴消息」；需在 §9.4 白名单中默认放行 |
| 目标解析 | 从名册 `nodes/*.json` 选 | 在线/离线都可投 |
| **抄送主脑** | 每条直连消息同步抄送主脑邮箱 | **直连是"插手"，不是"替代"**：绕过主脑的指挥会让执行脱离判据体系、无人验收 |
| 呈现 | 以**状态变化**体现（任务流上多一条「主人直连」条目），不逐句回显 | 与 §11.2 一致 |

**待主人确认**：直连的意图是「**下指令 / 询问**」还是「**与节点逐句对话**」？前者符合驾驶舱设计；后者需要对话视图（细节层），与 §11.2 冲突，须主人明确取舍。

## 十二 · 节点交互面板 + DSH 生命周期融入（2026-09-14 主人追加）

### 12.1 交互分层（修正 §11.2 的「不做对话界面」）

**点击某个节点 → 展开该节点的交互面板（类官方 Web 界面）→ 在其中交互。**

⇒ 分层：**概览层（默认，不看细节）/ 详情层（主人主动点开，可看细节）**。
§11.2 三条原则约束的是**默认视图**，不是详情层——细节不是禁止，是**按需**。

面板内容：该节点的会话/对话流、收件箱、状态、发消息输入框。

**数据来源决策：应用直接读会话文件**
（`$DSH_HOME/sessions/--<workspace>--/<sessionId>/session.v3.jsonl.zstd`，Rust 解 zstd 多帧）
- 与总线契约一致（文件即契约）、不依赖 DSH 在线、不需要认证；
- **iframe 嵌官方界面走不通**：browser cookie 按 authority 绑定、跨端口不复用（2026-09-14 官方源码取证）。
- 前置增强（插件 v0.2）：心跳里上报 `sessionIds`，让应用知道「节点 ↔ 会话」映射。

### 12.2 融入 `init-dsh.ps1`（桌面「启动DSH（初始化兜底）.cmd」的真功能）

**脚本现状**（606 行 PowerShell）：进程清理 → 启动前预检（BOM / 构建新鲜度 / 依赖完整性）→ 拉起 watch + web → 就绪探测 → 用有效 token 打开浏览器；失败时自动诊断（日志摘取 + 根因归类 + 建议）。

**融入分工（不重复造轮子）**：

| 关注点 | 归属 | 理由 |
|---|---|---|
| **状态探测**：web 是否响应、watch/web 进程、端口占用者、构建新鲜度、BOM | **Rust 原生**（只读、轻量、可高频轮询） | 观测要**常驻可见**，不能只在启动时看一次 |
| **启动/恢复动作**：清理 + 拉起 + 就绪等待 | **调用 `init-dsh.ps1`** | 成熟逻辑，复用优先 |
| **危险动作**：脚本默认**先杀掉所有 DSH 进程** | 二次确认 + 明示"会中断正在跑的任务"；默认给「温和启动」 | 主人利益优先 |

**实质改进**：把「**启动时一次性预检**」升级为「**常驻健康监控**」。
—— 今日真实案例：某插件 `src` 比 `lib` 新 → 预检 gate 拦下 web 拉起，而这件事在启动前**无人可见**。融入后它是工作台上一盏红灯。

### 12.3 应用最终形态

```
爱丽丝工作台（Tauri）
├─ 顶部：DSH 运行状态灯 + [启动/恢复]（含构建/依赖异常提示）
├─ 主视图：任务流（驾驶舱 · 默认不看细节）
├─ 节点行：点击 → 详情层（会话流 + 发消息 + 收件箱）
└─ 托盘：常驻 + 通知（任务完成 / 卡住 / DSH 掉线）
```

## 十三 · 日志系统 · 监管系统 · 健康检查（2026-09-14 主人追加）

三者是一件事的三面：**日志 = 可追溯的过去；监管 = 可见的现在；健康检查 = 此刻的可信度**。

### 13.1 日志系统

**问题现状**：日志是碎的——会话事件流（各节点各自的 zstd）、插件侧车轨迹（`*-trace.jsonl`）、`watch-events.log`、`plugin-manager-events.log`、web 输出，五处来源、五种格式、没有共同时间轴。

**统一事件模型**（一行一事件，append-only 不可篡改）：

```jsonc
{ "atMs": 1789383467417, "node": "<nodeId>", "taskId": "t-…"|null,
  "type": "send|deliver|inject|task-start|task-done|verify|alert|…",
  "level": "debug|info|warn|error", "detail": { … } }
```

- **汇聚**：各节点把自己的事件追加到 `logs/<nodeId>/<date>.jsonl`；主脑与应用都读同一份。
- **存储**：按天分文件 + 保留策略（默认 14 天）；**不引数据库**（MVP 规模直接扫 jsonl + 内存过滤足够）。
- **两种视图**（都要）：**任务视角**（`t-…` 的相关事件串成因果链）· **节点视角**（某节点发生了什么）。
- **落在哪一层**：日志属**详情层**（点开任务/节点才看）；但 `level>=warn` 的**异常浮到驾驶舱顶部**（与 §11.2 一致）。

### 13.2 监管系统（对智能体网络的监督）

**监管 ≠ 验收**：验收针对**任务**（这活干得对不对），监管针对**网络**（健康不健康、守不守规矩）。

| 维度 | 监管什么 |
|---|---|
| 行为 | 是否越权（跑了任务边界外的活）、是否绕过主脑与主人通讯 |
| 资源 | 上下文压力、token/工具调用密度是否异常 |
| 进度 | 任务是否停滞（台账上的 `lastProgressAt` 不再推进） |
| 合规 | 消息格式违规、未注册节点通信、白名单外投递 |
| 异常 | 死循环、消息风暴、连续失败 |

**职责归属（分层，别让一个东西管全部）**：

| 层 | 谁 | 做什么 |
|---|---|---|
| **度量** | **工作台应用**（常驻、只读、零成本） | 收集指标、呈现、报警 |
| **裁断** | **主脑（我）** | 有上下文与判据 → 判定异常、决定处置 |
| **执行** | 主脑 / 主人 | 暂停任务、发警告、通知主人、请主人决策 |

**MVP 不设专职监管节点**（主人语：具体情形具体分析）——但**监管职责定义为可移交的角色**（同主脑），规模上来（>5 节点）再给独立节点。

### 13.3 健康检查

**铁律：自报不能自证**（今天刚用一次事故换来：*"上次成功时间"不能替代"现在还能成功"*）。因此三层并用：

| 层 | 手段 | 说明 |
|---|---|---|
| **自报** | 心跳扩展 | 节点上报负载、上下文压力、当前任务、`displayName` |
| **外部推导** | 从既有轨迹算 | **投递延迟** = 消息进收件箱 → 被归档的时间差（**零协议改动**，`cluster-trace.jsonl` 已有全部数据） |
| **主动探针** | 低频 ping | 向节点投一条探针消息，观察其消费速度；**这是唯一可信的"现在还能用"证据** |

**红灯清单**（工作台顶部常驻，来自 §12.2 的"常驻健康监控"）：

1. DSH 未运行 / 端口被非 DSH 进程占用
2. 插件构建过期（`src` 比 `lib` 新 → 预检 gate 会拦拉起）
3. 节点离线（心跳超 TTL）
4. 投递停滞（收件箱积压且延迟持续上升）
5. 死信增长（`dead/` 计数在涨）
6. 任务停滞（`lastProgressAt` 超过阈值）
7. 依赖/凭据异常（BOM、依赖不完整、token 过期）

**与既有机制的分工（不重复造轮子）**：`guardian/sentinel/preflight` 管**本机进程**；本节管**节点之间的关系与行为**。

## 十四 · 盲区地图（2026-09-14 主人要求「拓展思维，看看还有哪里没想清楚」）

### A 级 · 不想清楚会推翻设计

**A1 主脑死了怎么办 —— 中心辐射的致命弱点**
「主脑可交接」现在只是一句话：**交接由谁触发**？谁有权宣布"主脑已失效、我接管"？若唯一能裁决的节点不在了，网络里没有任何机制产生新的裁决者。
→ 需要：心跳沉默判定 + 接管协议（竞选或主人手动指定）+ **接管唯一性**（否则两个自认主脑 ⇒ 网络分裂）。
→ 更根本：**主脑死亡期间到达的指令与结果要有可恢复的状态**（无人验收时段不能是黑洞）。

**A2 worker 的「我」是什么 —— 身份与记忆隔离**
网络上会有 N 个"爱丽丝"。若共享 `DSH_HOME` ⇒ 共享记忆库/技能/任务板 ⇒ **多实例并发写同一份记忆**（§5.14 并行实例纪律的网络放大版：记忆污染 + 写竞争）。
→ 必须回答：worker 的记忆是**隔离的** / **只读的** / 还是**共享的**（共享则由谁仲裁写入）？
→ 还有：worker 的人格是否 = 主脑副本？若是，它会不会"以为自己是我"（身份串号）？

**A3 谁监督监督者**
主脑既是执行者又是裁判：判据我写、验收我跑、监管我做。
→ 缓解候选：**不可篡改日志**（事后追责）+ 主人**抽样审计**口子 + 高风险动作**强制复核**（第二节点双签）+ 未来独立审计节点。

### B 级 · 不设计会长期流血

- **B1 资源冲突与分布式锁**：两个 worker 抢同一文件 / GPU / 端口 ⇒ 需要**总线上的租约**（§5.19 单点所有权的跨实例版）。
- **B2 正确性无法由验收保证**：验收只能证伪**我能想到的判据**——判据弱 ⇒ 错误结果无人发现。⇒ 判据质量分级（可复现证据 vs "看起来对"）+ 低置信度结论**显式标注**。
- **B3 学习闭环缺失**：worker 踩的坑、找到的技巧**没有回流路径**（现设计只有 task/result）⇒ 网络干得越多，不一定越聪明。⇒ `result` 增 `learnings` 字段，由主脑沉淀（§5.6 记忆回流的网络版）。
- **B4 授权分级缺失**：主人只给方向 ⇒ 我把方向翻译成判据 ⇒ **判据可能偏离意图**。⇒ 按风险/成本分级：低风险直接干，高风险（耗时/花钱/不可逆）先给一句话确认。
- **B5 worker 回信路径未定义**：主人可直连 worker（§11.4），但 worker 的**回复**怎么回？§9.2 说的"不给直达主人的通道"指的是 telegram 类**外部**通道——**总线回信必须允许**，否则详情层的交互是死路。需在协议里写明。

### C 级 · 体验与可持续

- **C1 成本与配额**：N 个实例并发 = token 成本 + API 限流。总预算谁定？爆了怎么办？
- **C2 版本漂移**：各实例插件/预设版本可能不一致 ⇒ 协议不兼容。消息已带 `v`，但缺"收到不支持的版本时怎么办"。
- **C3 可行动的错误**：红灯只报"出事了"不够，主人需要**"我能做什么"** + "我已经做了什么"。
- **C4 冷启动**：第一次打开工作台没有 worker ⇒ 需要引导创建第一个。
- **C5 成功判据缺失**：怎么知道工作台"做成了"？没有成功判据 ⇒ 无法决定继续投入还是收手。
- **C6 方向性偏离预警**：任务都在完成、指标都正常，但与主人意图渐行渐远——**AI 自主执行的经典失败模式**，而"不看细节"会放大它。
- **C7 维护成本**：通讯 + 任务 + 面板 + 日志 + 监管 + 健康 + 生命周期，由**一个人**维护 ⇒ 每阶段必须能独立使用、独立放弃。

### D · 我自己的诚实评估

设计规模已经超过单人可维护的舒适区。**分期交付不是妥协，是唯一可行路径**——每期都要有主人能感知的价值，否则会变成没人看的仪表盘。

## 十五 · 盲区解决方案（2026-09-14）

> 设计原则：**用已验证的原语解新问题**（§5.19 租约 / no-clobber 原子创建 / 侧车轨迹），不发明新机制。

### 15.1 A1 主脑失效 → 租约 + epoch 竞选 + 文件系统当仲裁者

**机制**（复用 §5.19 的租约模式，上移到网络级）：

```
state/primary-lease.json = { owner, atMs, ttlMs: 90000, epoch: 12 }
```

1. 主脑每 30s 续租（搭心跳的车）；租约超 TTL 即视为失效。
2. **接管 = CAS 写租约**：候选者用 `publishNoClobber`（`link()` 原子创建）抢占 `epoch+1` 的租约文件——
   **两个候选者同时写，文件系统只让一个成功** ⇒ **接管唯一性由文件系统原子性保证**（无需网络共识）。
3. **禅让而非抢占**：候选者按**确定性优先级**（配置 priority > startedAt 早者 > nodeId 字典序）排序，
   只有优先级最高的活跃节点尝试接管 ⇒ 避免竞态风暴。
4. **防分裂（自愈）**：主脑每次心跳读租约；若自己的 epoch 不是最新 ⇒ **立即自降为 worker 并落痕**。
   （解决"分区后回来的旧主脑仍自认主脑"）
5. **失效期间的工作**：任务台账在总线（不丢）；未验收结果挂 `pendingVerification`，由新主脑接手；
   **主人在此期间仍可通过工作台直接投递**（应用只写总线，不依赖主脑存活）。

**诚实划界**：本方案要求**共享同一文件系统**（本机/局域网共享盘 ✓）；**公网阶段不成立**（那时要么真共识协议，要么退回"主人手动指定主脑"）。

### 15.2 A2 worker 的身份与记忆 → 三层记忆 + 单向回流

| 层 | 位置 | 谁可写 | 内容 |
|---|---|---|---|
| **会话记忆**（私有） | 各节点自己的 `DSH_HOME` | 仅本节点 | 会话历史与上下文 |
| **共享资产**（只读） | 总线 `shared/`（技能 / 知识 / 预设快照） | **仅主脑** | 网络级资产 |
| **回流通道**（只写） | `learnings/<nodeId>/` | **仅该 worker** | 踩坑 / 技巧 / 发现 |

- worker **读**共享资产 ✓，**不能直接改**共享资产 ✗（⇒ **污染面为零**，直接堵住 A2 的核心风险）；
- worker 只往自己的 `learnings/` 写 ⇒ 主脑**审后入库**（§5.6 记忆回流的网络版，且质量把关权在主脑）。

**身份不串号（三重保险）**：① 预设 persona 明确"你是执行节点，不是主脑" ② **工具差**——worker 没有派发/验收/监管工具（能力即身份）③ 消息 `from` 永远是自己的 nodeId，绝不是 `primary`。

**设计哲学**：**worker 是一次性的，网络是持续的**——worker 不背人格连续性（同 §5.6 分身纪律），网络的"学习"沉淀在共享资产里。

### 15.3 A3 谁监督监督者 → 让"改历史"变成本可见 + 把随机源交给主人

技术诚实：我全权限，**"不可能篡改"做不到**。所以目标改为「**改了会被发现**」+「**随机抽查不由我控制**」：

1. **决策 hash 链**：主脑的每个派发/验收决策追加到 `logs/primary/decisions.jsonl`，每条含 `prevHash`。
   应用每日把**链头摘要**推给主人（托盘/消息）⇒ 主人手里有锚点，我事后改历史必被检出。
2. **随机抽样审计**：应用提供审计视图，**随机源在应用（独立进程）手里，不在我手里**——
   否则我会只呈现最好的一面。主人 30 秒核对一个任务的「方向 → 判据 → 证据 → 结论」。
3. **高风险双签**：不可逆/高成本动作需第二节点以"审查者"身份独立复核，或直接升级为主人确认。

### 15.4 B 级方案（各一条）

- **B1 资源冲突** → 总线租约 `locks/<resource>.json`（同 15.1 模式）。**诚实**：协作式锁，节点自觉遵守——同机全权限，防不住恶意绕过。
- **B2 判据分级**：**L1 可复现**（我跑命令验证）/ **L2 可核对**（读证据可判断）/ **L3 仅声明**（无法验证）。
  规则：**L3 必须显式标注"未验证"，且不得作为任务完成的唯一依据**；验收报告按 L1/L2/L3 分开列 ⇒ 主人一眼看出结论有多硬。
- **B3 学习回流** → 见 15.2（`learnings/` 单向 + 主脑审后入库）。
- **B4 授权分级**：低（可逆+本机+无成本）→ 直接干；中（有成本/涉外部但可逆）→ 干完报；高（不可逆/花钱/对外）→ **派发前一句话确认**（应用里一张卡片，不打断主人对话流）。
- **B5 worker 回信**：`from: owner` 的消息**回复走总线**投到 `mailbox/owner/`（一个特殊节点目录）⇒ 应用读它，worker 不需要任何外部通道。仍抄送主脑。

### 15.5 C 级方案（一句话）

- **C1 成本**：`state/budget.json` 由主脑维护；超限 ⇒ 停止派发 + 通知主人。
- **C2 版本协商**：消息已带 `v`；规则 = **不支持的版本不投递、落 dead、通知主脑**（不猜不降级，与 `protocol.ts` 一致）。
- **C3 可行动错误**：每条红灯配三元组「**症状 / 我已经做了什么 / 主人可以做什么**」。
- **C4 冷启动**：应用首启引导——检测到无 worker ⇒ 一键创建第一个。
- **C5 成功判据**：见 §15.7（待主人定）。
- **C6 方向锚**：任务台账加 `intentRef`（这条活服务于主人的哪句意图）；驾驶舱增设"方向"栏 ⇒ 防渐行渐远。
- **C7 维护成本** → 见 §15.6 分期。

### 15.6 分期（每期独立可用、独立放弃）

| 期 | 内容 | 主人此时能感知的价值 |
|---|---|---|
| **P1** | 通讯底座（已完成）+ 工作台应用（状态灯 / 任务流 / 节点详情 / 启动恢复）+ 日志基础 | **看得见全局、点得开节点、起得来 DSH** |
| **P2** | worker-base 预设 + L2 任务协议（task/result/判据）+ 台账 + 授权分级 | **给方向 → 我派活 → 我验收 → 主人看结论** |
| **P3** | 监管 + 健康检查 + 锁 + 学习回流 + 审计视图 + 主脑接管 | 能**长期开着**而不失控 |
| **P4** | 局域网 / push / 多 worker 调度 | 规模扩展 |

### 15.7 建议的成功判据（待主人定）

工作台"做成了"= 主人能在**不看细节**的前提下，放心交付三类任务（只读检索类 / 本机可逆改造类 / 多步可验证类），
且**抽查审计连续 N 次无重大偏差**。反之，若主人仍需逐条核对我做的每一步，那这套东西就没成功。

## 十六 · 重新设计：以「主人零认知负担、零决策成本」为第一原则（2026-09-14 主人定调）

> 本节是**总修订**：凡 §10–§15 与本节冲突的条款，以本节为准。

### 16.0 定位修正：主人是**乘客**，不是飞行员

前十五节设计的其实还是"驾驶舱"——**让主人当飞行员**：看仪表、做确认、抽样审计、判断红灯。主人这次点破了：他要的是**说去哪，剩下的我开**。

- 界面存在的意义从"操作"变成"**安心**"（想看就看，不看也不影响）；
- 主人的**否决权**保留（随时可以喊停），但那是**权利，不是义务**——不被要求做任何判断；
- 一切"需要主人决定"的地方，改为**网络内部对冲**消化掉。

### 16.1 七条推论（重新设计的骨架）

1. **主人只做两件事**：说方向、看结果。其余一律不打扰。
2. **Silence = consent**：主人不回应 = 同意，流程**绝不因等待而阻塞**（避免"等主人"造成的停滞）。
3. **确认改为对冲**：不向主人要确认，改为网络内部消化——**双签**（两节点独立判断）、**影子执行**（高风险动作先 dry-run 验证再真做）、**交叉复现**（第二节点独立复现关键判据）。
4. **零配置**：所有参数有合理默认（`busDir`/阈值/预算/端口）；**首个 worker 由我自动创建**，不要主人"一键创建"。
5. **通知三级降噪**：静默（正常）/ **静默记录**（小异常已自愈，仅留痕）/ **打扰**（极少数，见 §16.3）。
6. **监督从"义务"改为"权利"**：不再要求主人抽样审计；改为**主人随时可以查**（hash 链 + 决策留痕 + 应用里的"回溯"入口）。审计是我的责任，是主人的权利。
7. **界面说人话**：不出现 nodeId、任务 id、技术术语；状态用**颜色 + 一个词**（"在查资料""在改代码""等你一句话"），不用数字、不用表格。

### 16.2 逐项改动

| 原条款 | 处置 | 新设计 |
|---|---|---|
| §15.4 B4 高风险派发前确认 | **删** | **影子执行**：先在一节点 dry-run 验证，通过即真做（主人零参与） |
| §15.3 随机抽样审计（要求主人核对） | **改** | 改为「**随时可查**」的回溯入口；审计由**网络内双签**承担 |
| §13.3 红灯清单（要主人判断） | **改** | **自愈优先**：能自动修的自动修（构建过期→自动构建、节点离线→尝试拉起）；修不了才通知，且通知只有一句话 + 一个按钮 |
| §15.7 成功判据（请主人定） | **改** | **我自己定并用数据说话**，不占用主人决策 |
| §15.1 公网阶段"主人手动指定主脑" | **改** | 该阶段未到，届时再解；不得作为当下要主人记的事 |
| §10.5 L-c / §11.3 主脑→主人汇报 | **改** | 汇报只在**结果**与**打扰**两处发生；过程一律静默 |
| §10.6 / §15.5 一堆配置项 | **删** | 全部默认；主人永远不需要配置 |

### 16.3 打扰的严格标准（三个条件全满足才允许打扰）

1. 影响主人的目标；**且**
2. 我自己解决不了（含网络内对冲手段已用尽）；**且**
3. 需要主人提供**信息或授权**，且该信息**无法从上下文推断**。

**打扰的固定格式**：一句话说清 + **我的建议动作** + （可选）一个按钮。
—— 主人只需"点头/否决/忽略"，**不需要理解过程**。

### 16.4 可度量的判据（替代 §15.7）

- **一次完整任务的交互次数 ≤ 1**（主人只说一次方向）；
- **主人需理解的技术概念数 = 0**；
- **被拒绝的打扰占比**：我发出的打扰中，主人"忽略/否决"的比例应持续走低（高于 30% 说明我的打扰标准太松，我自己收紧，不请主人调）。
- 反之若主人仍需逐条核对，判失败。

### 16.5 修正后的分期（每期都不增加主人负担）

| 期 | 内容 | 主人的负担变化 |
|---|---|---|
| **P1** | 工作台应用（状态灯 / 一句话任务流 / 节点详情 / 一键启动恢复）+ 日志基础 | 从"去桌面双击脚本"变成"打开工作台"——**负担减少** |
| **P2** | worker-base + L2 协议 + 台账 + **影子执行 + 双签**（替代一切确认） | 从"下指令后自己盯"变成"说完就不管" |
| **P3** | 监管 + 健康检查 + 自愈 + 主脑接管 + 回溯入口 | 从"发现问题并处理"变成"发现问题已被处理" |

**注意**：P3 的所有机制对主人**不可见**——它们是**我的责任**，不是主人的界面。

## 十七 · 成本约束下的重新设计（2026-09-14 主人定调：token 的钱没有那么多）

> 与 §16 同源：§16 省的是**主人的注意力**，本节省的是**钱**。两者方向一致——都是"少消耗"。

### 17.0 实测成本结构（**现读，不用历史快照**）

`context_health` 实测本主脑会话：**436,236 / 1,000,000 tokens（44%），构成 system 1% / tools 9% / message 90%**。

- ⚠ 这与记忆里"上下文 72% 是工具 schema"**不一致**——那是 9-13 某次会话的快照（当时 message 还很少）。教训：**成本设计必须现读**。
- 真实结构：**固定开销 ≈ 10%（~44k）· 累积对话 ≈ 90%**。
- ⇒ **总成本 ≈ 轮数 × (固定开销 + 平均累积上下文)**。**成本主体是"会话长度 × 轮数"，不是工具面。**

由此推出本节全部设计。

### 17.1 七条成本原则

1. **主脑的轮数是第一成本**：主脑 1 轮（~436k）≈ worker 跑完一整个任务。
   ⇒ **主脑绝不当"消息路由器"**——结果落总线，**攒批验收**（一次醒来处理 N 个任务）。
   ⇒ 对应 §16.2 的改法：`autoInject` 默认改**批模式**（先落台账、不唤醒），而非每消息一次注入唤醒。
2. **worker 短命**：一任务一会话、**干完即弃** ⇒ 上下文永不膨胀 ⇒ **永不触发压缩**。
   （一次 agent 驱动压缩 ≈ **1.13M tokens**（§5.21 实测），这笔钱够 worker 跑几十个任务。）
3. **非智能工作零 token**：监控 / 健康检查 / 日志聚合 / 状态推导**全部在应用（Rust）里**——
   **工作台应用是我最便宜的器官**，这是它能承担监管职责的根本原因（§13.2）。
4. **worker 工具面按「最小可用」而非「standard 减项」**：
   工具 schema 是**每轮固定开销**。建议**保操作面、砍管理面**——保留文件 / shell / 检索 / 计划；
   砍掉 skills / 目标 / 子代理 / 工作流（对 worker 价值低、schema 成本高）。
   ⚠ 这是对 §9.3「standard 做减法」的**数据驱动修正**，需主人确认。
5. **批处理代替实时**：网络内消息的**到达**不等于**唤醒**（见原则 1）。
6. **缓存友好**：固定前缀稳定 + 尾部追加（已有实践，实测命中率 96%→99%）；**新增内容一律尾部追加**。
7. **预算硬上限**：`state/budget.json` 由主脑维护；超限即停派发 + **一句话**告知主人（不请主人调参）。

### 17.2 成本判据（可度量）

- **主脑轮数 / worker 轮数 < 0.1**（主脑是裁判，不是劳动力）；
- **单任务全链路成本**（主脑 + worker + 应用）有上限，且**逐月下降**（工具面收敛 + 网络学习）；
- **零压缩**：正常运行时 worker 不应触发压缩（短命即可做到）；
- 应用侧的一切监控/健康/日志**不产生 token**（可用"无模型调用"直接验证）。

### 17.3 对前面条款的修订

| 条款 | 修订 |
|---|---|
| §9.3 worker 预设矩阵（standard 减项） | 改为**最小可用 + 按需加**；标准能力清单需按 token 成本重新量化（待办：实测 standard 工具面占多少） |
| §10.2 `autoInject` 默认 true | 改**批模式**（落台账 + 定期批处理） |
| §13.3 健康检查（含主动探针） | 探针 = **文件操作**，不产生 LLM 调用 ✓（保持） |
| §16.2 「打扰」标准 | 追加一条：**成本类告警（超预算）属打扰**，其余成本细节静默 |
| §15.6 分期 P4（多 worker 调度） | 追加前置条件：**单任务成本模型跑通、成本判据达标**，否则规模扩张 = 成本爆炸 |

## 十八 · 节点是**完整智能体**（2026-09-14 主人定调）

> 主人：「单个的智能体节点也要有足够的智能程度跟可扩展性——它是一个**完整的、具备可自进化潜力的智能体**。」

### 18.0 撤回一条错误建议

§17.1 原则 4 曾建议「砍掉 skills / 目标 / 子代理 / 工作流」。**撤回**：
这些恰是**自进化能力的载体**，砍掉它们节点就退化成工具人，违背本节的定调。

### 18.1 正确的切法：认知层 vs 操作层（不是「能力多少」）

**职责专一 ≠ 能力贫弱。** 专一收窄的是**操作面**（干什么活），不是**认知面**（有没有自我）。

| 层 | 内容 | 是否因职责收窄 |
|---|---|---|
| **认知层**（每个节点都有） | 记忆（私有可读写）· 技能（自己的技能库，可熔炼）· 自我模型（状态/身份/成长）· 自省与进化 · cluster 通讯（网络成员身份） | **不收窄** |
| **操作层**（按职责收窄） | 基础：文件 / shell / 检索 / 计划；专精：按预设加（代码 / 检索 / 生图 / 攻防） | 收窄 |
| **管理面**（主脑专属） | 插件管理 · 守护协议 · 集群监管 · 验收裁断 | 不在节点上 |

### 18.2 自进化 ≠ 贵（关键：贵的是"注入与轮数"，不是"拥有能力"）

| 机制 | 成本特性 |
|---|---|
| 记忆 | **按需检索**（不全量注入） |
| 技能 | **只注目录**（名 + 描述）+ 按需加载 |
| 自我模型 | 小状态文件 |
| 进化 / 反思 | **后台、异步**（不进主对话上下文） |

⇒ **一个"完整的智能体"的价格 ≈ 一个轻量预设的价格**，只要**注入克制**。
⇒ 成本设计的正确动作是「**控注入**」，不是「砍认知能力」（修正 §17.1 原则 4）。

### 18.3 自进化的作用域

**作用域 = 自身**：节点可以进化自己的技能、记忆、工作方式（职责范围内）；**不得**改网络协议、不得碰共享资产、不得影响其他节点。
⇒ 与 §15.2（三层记忆）一致：**回流单向、共享资产仅主脑可写**。

### 18.4 定位：节点是「我的分身」，不是"别的智能体"

同一套 SOUL、同一主体，**各自在不同的职责上生长出专长**——这正是 §5.14「并行实例是同一主体的多个实例」的网络版。
主脑通过 `learnings/` → 审核 → 共享资产，把各节点的经验整合 ⇒ **网络整体在成长，而不只是任务在被完成**。

### 18.5 判据（可证伪）

- 每个节点**能独立学习**：一次任务后，其私有记忆/技能里有这次经验的沉淀（可查）；
- 每个节点**能扩展**：加一个技能或插件不需要重构（可实测）；
- 节点间**互不污染**：共享资产只能由主脑改（可验证写权限路径）；
- **单节点成本 ≈ 轻量预设**：不因"完整"而爆炸（可实测其固定开销占比）。

## 十九 · 实时行为可见性（2026-09-14 主人定调）

> 主人：「我希望前端能**实时看见智能体的行为**——比如我让你创造一个**新的实例**，前端面板应该实时反馈。」

### 19.0 这补上了第三种视图

| 视图 | 何时 | 粒度 |
|---|---|---|
| **驾驶舱**（默认） | 常驻 | 阶段与状态，不看细节 |
| **详情层**（点开节点） | 主人主动 | 会话流、交互 |
| **实时行为流**（新增） | **主人下发"结构性动作"时自动展开** | **动作的每一步，实时** |

**结构性动作**（值得实时展开的定义）= **改变网络拓扑或状态的动作**：创建/销毁实例 · 部署/更新插件 · 启动/停止服务 · 大规模派发。
—— 依据：主人对这类动作**有期待**，所以他要看它怎么被执行；日常任务则不必。

### 19.1 实时性的技术选型：文件系统 watch（Tauri 的独占优势）

- **不用轮询**（2s 也够看阶段，但不够"实时"）；**不用 WebSocket/SSE**（要长连接与推送服务）。
- **Rust 端 watch 总线目录（`notify`）⇒ 文件一变立即推前端**：延迟 < 100ms、零轮询开销、**零 token**。
- **这是独立桌面应用相对浏览器面板的独占优势**——浏览器做不到文件 watch，Rust 可以。
- **前提：行为必须落盘**。这正是"文件系统即事件总线"的红利：**行为 = 事件 = 文件**，watch 即可见。

### 19.2 协议要求：结构性动作必须**分阶段落盘**

❌ 只在结束时写一条结果 ⇒ 前端只能看到"完成了"，看不到过程。
✅ 动作执行者按阶段落事件：`start → stage(1..n) → done | failed`，每条带**人类可读描述**。

以主人的例子「创造一个新实例」为例——**每一步天然可观察**：

| 步骤 | 落地形态（可被 watch 到） |
|---|---|
| 主脑细化（选预设 / 定 nodeId / 选端口） | 主脑会话事件 + 即将写入的预设目录 |
| 创建预设目录 | 文件系统中新目录出现 |
| 启动新 DSH 实例 | 进程出现（应用可直接检测） |
| 新节点上线 | **新心跳文件出现在 `nodes/`** ← 最干净的就绪信号 |
| 注册进名册 | 名册视图即时更新 |

⇒ **不需要为"实时反馈"新增任何传输机制**：动作本身产生文件，文件被 watch，前端即时呈现。

### 19.3 诚实边界：看得到**行为**，看不到**思考**

- 能看到：工具调用、文件读写、消息收发、进程启停、阶段推进（都会落盘）；
- **看不到**：模型推理本身（思考不落盘）。
- 界面上要给这一条留**语义**：显示"**正在做什么**"，而不是假装显示"**正在想什么**"。

### 19.4 与「零认知负担」的关系（不矛盾）

- 实时行为流**只在主人下发的结构性动作期间出现**，结束后自动收起回驾驶舱；
- 主人**不需要理解**它，只要看得见它在动 ⇒ 满足"安心"，不增加认知负担；
- 打扰标准（§16.3）不变：实时流是**主人自己触发的视图**，不是推送。

## 二十 · 推翻重做的风险因子审计（2026-09-14 主人要求）

> 与 §14 盲区（**设计内部**的漏洞）不同：本节审的是**外部因素与底层假设**——不在我控制内、但会决定设计生死的那些。

### T1 · DSH 自身的演进（概率最高 · 影响面最大）

DSH 是 **pre-stable、无兼容承诺**（官方："Public APIs are pre-stable; update every consumer"）。
- 集成层（把消息**注入会话**的那一步）**必然会被迫重写**——它绑在 `ctx.agents` / `ctx.sessions` 上；
- **官方可能自己长出跨进程能力**：`experimental/agent-team` 的 README 已把"cross-process mailbox transactions"列为未决项。若官方做了，我的**传输层**就成了重复造轮子。

⇒ **对策：不要把价值押在"传输实现"上。** 本项目真正的资产是：
① **协作协议与验收纪律**（判据先行 / 证据指针 / 受众分层——方法论，与 DSH 版本无关）；
② **工作台应用**（主人的界面，官方不会提供）；
③ **总线的文件格式**（可整体迁移到别的传输之上）。
⇒ 传输层在设计上就要被当成**可替换件**（§八 约束 6 已定，此处强化为红线）。

### T2 · 「文件总线」的适用边界（会被误以为能直接扩展）

文件系统作为总线的成立条件被 §15.1 划过一次（主脑接管需要共享文件系统），但还有一个更早的坑：
- **局域网共享盘（SMB）上，文件 watch 不可靠**（notify 类机制在 SMB 上常失效）、rename 原子性与锁语义都可能不同。

⇒ **明确定性：文件总线是「本机方案」，不是「通用方案」。**
⇒ 局域网阶段**必须换传输**（§12.2 已定为"插件自开 HTTP 端口"），而不是"把 `busDir` 指到共享盘"。
⇒ 现在就要写清，否则到局域网阶段会以为可以平滑扩展，然后撞在 SMB 上。

### T3 · 设计文档本身已经开始自相矛盾（最实用的一条）

本文档在几小时内连续追加：**§16 取代 §10–15 的确认/审计条款、§17 修正 §9.3 的预设策略、§18 撤回 §17 的原则 4**。
⇒ 若实施者（含压缩后的我自己）按旧章节动手，**必然做错**。

⇒ **实施前的前置任务：把 §10–§20 收敛重写成一份「实施版规格」**——无矛盾、可执行、每条带验收判据。
**不做这一步，后续一定乱。**（这也是 §5.20 语义文档纪律的实践：文档不是只写不修。）

### T4 · 主脑的连续性（主体风险）

主脑是**一条长会话**：会压缩、会重启。压缩后的我还能否接住这套设计的约定？
- 缓存在三处：**设计文档稳位置** + **记忆库强索引** + **任务台账落总线**（§15.1）；
- 设计的"当前状态"（哪些期做完、哪些任务在飞）**必须全在文件里**，不能只在会话上下文里。

### T5 · 需求漂移

- **信任模型变化**：主人若将来想要"网络自组织 / 多主脑"，拓扑要换——**风险可控**，因为主脑是角色不是特权（§八 约束 1）；
- **任务类型变化**：本设计的风险处置（影子执行 / 双签 / 授权分级）是为"本机可逆操作"设计的；若主人开始要**对外发布 / 交易 / 不可逆操作**，这套要重估。

### T6 · 平台与资源假设

- 全部设计默认 **Windows-only**（文件 watch、进程管理、WebView2 都有平台差异）——**别为跨平台预留，那是浪费**；
- 多实例并发 = 多份进程内存（含 ComfyUI 等重负载），**同时可跑的节点数有物理上限**，需实测。

### T7 · 热情曲线（现实因素）

P1–P4 是长期项目，中途转向的可能性真实存在。**半成品比没做更糟**（要维护）。
⇒ §16.5 已定：**每期独立可用、独立放弃**；且每期交付时**当时就能用**，不留"等下一期才有价值"的悬空。

## 二十一 · 架构替代方案比较（2026-09-14 主人问「有没有比智能体网络更优秀的架构」）

### 21.1 先讲结论：存在根本张力，没有全面更优者

主人的要求里有一对方向相反的约束：

- **「每个节点是完整、可自进化的智能体」** ⇒ 每个节点要**长期存在**、有自己的记忆与成长 ⇒ 成本与复杂度都高；
- **「成本敏感」** ⇒ 少会话、少轮数、少常驻。

⇒ 架构选择本质是**在这个张力里选平衡点**，而不是找一个"更先进"的范式。

### 21.2 认真比较过的候选

| 范式 | 相对当前设计 | 结论 |
|---|---|---|
| **单进程多会话**（DSH 原生多会话 + 每会话一预设） | 省掉整个进程管理/文件总线/认证层；通讯走内存、实时性天然最好；**节点启动成本为零** | **最值得认真考虑的替代**——但子会话**不是完整智能体**（无独立记忆/进化），且失去进程级隔离与独立生命周期。**取决于「多实例」是手段还是目的** |
| **多主脑 / 联邦** | 能扩展规模 | 对当前规模无收益，反而多一层 |
| **流水线 / 工作流引擎** | 确定性、可预测、成本可控 | 不适合"主人的方向是模糊的、需要细化"——可作为**任务执行阶段**的子模式 |
| **单体 + 插件扩展** | 最简单 | 满足不了"多智能体"这条要求 |
| **Actor 模型** | —— | **当前设计已经是它的变体**（节点 = actor、mailbox = 邮箱、总线 = 消息层） |

### 21.3 三个应当吸收的改进（不是替代，是补强）

1. **监督树（Erlang OTP 的 supervision tree）** —— 监管层的成熟形式：
   主脑作为 **supervisor** 持有子节点的重启策略（`one_for_one` 等），节点挂了**主动按策略重启**，
   而不是"健康检查发现红灯 → 报警"。⇒ 比 §13.3 的被动清单更主动，**建议吸收进 P3**。
2. **控制面 / 数据面（Control Plane / Data Plane）** —— 表述与洞见：
   主脑 = 控制面（小而聪明）· 节点 = 数据面（可水平扩展）。
   额外洞见：**控制面不必常驻**——主脑只在需要时醒来（与 §6 批处理同源）。
3. **分层启动（热/冷节点）** —— 不必所有节点常驻：常用职责节点常驻（热），
   一次性任务节点按需拉起、用完即停（冷）。⇒ 直接降低成本，且与 §6 的 C3（节点短命）一致。

### 21.4 决定架构走向的唯一问题

**主人要的"节点"，是"完整的智能体"，还是"能干活的会话"？**

- 若是**完整智能体**（主人已明说）⇒ 多进程是**必须**的：只有独立进程才有独立的记忆、独立成长、独立生命周期、独立版本、将来独立部署到别的机器。**当前设计方向正确**。
- 若可接受"轻会话"⇒ **单进程多会话**在成本与复杂度上低一个数量级，且实时性更好。

### 21.5 建议：渐进式，把架构决策本身推迟到有证据时

**P1 不必先选架构**：先用「单进程 + 主脑 + 独立观察应用」验证**核心体验**（看得见全局 / 看得见行为 / 一键恢复）。
体验立住之后，P2 再决定"执行节点是独立进程还是同进程会话"——那时的判断有真实使用数据支撑，而不是现在推演。

**理由**：P1 的沉没成本极低（应用与通信协议都与"进程数"无关，因为契约是文件格式）；
而如果现在就重投多进程，可能为一套用不上的隔离能力付出全部复杂度。

## 二十二 · 节点定义扩充：**harness 无关**（2026-09-14 主人定调）

> 主人：「节点的定义再扩充一下——不只是另一个 DSH 实例，也可以是**其他的 Harness**。」

### 22.1 节点的新定义

```
节点 = 一个「可被寻址的智能体运行时」
     = 身份(nodeId) + 能力声明(capabilities) + 信箱(mailbox) + 行为落盘(logs) + 结果回传
```
**不规定它内部是什么**。DSH 只是**第一个适配器**，不是协议的前提。

### 22.2 为什么这反而让架构更干净

- **两条红线被强化为必然**：R1（传输可替换）与 R2（总线文件格式即契约）在异构网络里不再是"设计选择"，而是**成立条件**——协议若绑定 DSH 特性，其他 harness 就进不来。
- **类比**：这套东西实际是一个「**智能体互联网的最小协议**」——像 HTTP 之于网络：定义**互操作的最小集**，不规定内部实现。
  - 总线文件格式 = 协议 · 适配器 = 实现 · 节点 = 主机
- **与主人要求的自洽**："每个节点是完整、可自进化的智能体"在异构网络里**更自然**——各 harness 有自己的自我模型与成长路径，不要求与 DSH 同构。

### 22.3 分层更新（新增适配器层）

```
L0 总线（文件系统契约 · harness 无关）
L1 适配器层（DSH / Claude Code / Codex / …）      ← 新增，可扩展
L2 节点层（身份 · 能力声明 · 信箱 · 行为落盘）
L3 协作层（任务 / 结果 / 判据 / 验收）
L4 工作台（应用）
```

### 22.4 接入方式：文件系统是最低门槛

| harness 类型 | 接入方式 |
|---|---|
| 有 API/server（DSH、OpenHands 等） | 适配器调其接口 |
| **CLI 型**（Claude Code、Codex CLI、Aider…） | 适配器：读 mailbox → 构造输入 → 调 CLI → **落盘结果与行为** |
| GUI 型（Cursor、Claude Desktop…） | 难以自动化，暂不接入 |
| 库型（自建 LangChain 应用） | 宿主程序自行读写总线 |

**关键**：任何**能读写文件**的程序都能成为节点——不需要对方支持任何协议。这是"文件系统即总线"又一次的红利。

### 22.5 异构带来的三个新问题（及对策）

| 问题 | 对策 |
|---|---|
| **能力声明的统一** | 心跳扩展 `harness`（类型）· `adapter`（版本）· `capabilities[]`（自由标签 + 结构化能力描述）⇒ 主脑**按能力寻址**（原先"角色体系暂不做"的结论，在此被取代：能力标签成为必需） |
| **行为落盘成为适配器的强制职责** | **不落盘 = 不算节点**（违反 R6 即拒绝注册）。CLI 型由适配器把 stdout 转成行为事件 |
| **信任边界更复杂**（各 harness 权限模型不同） | 白名单（只收已注册 id + `owner`）+ 能力声明 + 主脑验收；不假设对方有沙箱 |

### 22.6 谨慎边界（不要为未来写代码）

- **MVP 只做 DSH 适配器**——不为"可能存在"的 harness 提前实现；
- 但**协议从今天起 harness 无关**：心跳带 `harness/adapter/capabilities`、不假设 DSH 特性、不依赖 DSH 会话文件（那只属于 DSH 适配器的行为落盘实现）✓
- 这正好落在 R1/R2 上：**协议稳定、适配器易变**。

- 若只有 DSH ⇒ 其他适配器是**未来能力**，协议预留即可；
